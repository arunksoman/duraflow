---
title: Execution
description: How a saved workflow becomes a Temporal worker, and how runs and schedules start.
---

Duraflow doesn't run workflows itself. Every workflow is executed by a Zigflow worker on Temporal,
exactly as it would be outside Duraflow. The backend's job is to keep the right workers running
and to talk to Temporal.

## One worker per workflow

The backend's `WorkerManager` (`internal/temporalexec/manager.go`) keeps one `zigflow run`
subprocess for every workflow with a DSL:

1. On save, the DSL is written to `<workflowsDir>/<workflow id>.yaml`.
2. Any running worker for that workflow is stopped, and a new one is started on the file. Zigflow
   has no hot reload, so this happens on every change.
3. The worker registers the document's `workflowType` (and any
   [named workflows](/docs/dsl/named-workflows)) on its `taskQueue`, and polls Temporal.
4. The save waits (up to 15 seconds) until the worker's health endpoint reports ready, so a run
   started right after doesn't find the task queue empty.

Each worker gets free loopback ports for its metrics and health servers, instead of Zigflow's
fixed defaults, so any number of them can run side by side. Its output goes to the backend's log,
prefixed with `[worker:<name>]`. On boot, the backend starts a worker for every stored workflow.

## Starting a run

`POST /api/workflows/{id}/executions` creates an `Execution` row and calls Temporal's
`ExecuteWorkflow` with the workflow's type, task queue and input. If Temporal is unreachable, or no
worker is polling the task queue, it fails rather than pretending.

Temporal doesn't announce that a run has finished, so the backend watches each running execution
in a goroutine and records its final status, output and error when Temporal reports it. Running
executions are picked up again after a restart.

## How Zigflow runs a document

Some tasks run as **separate Temporal workflows**, not inside the parent's history:

| Task | Runs as |
| --- | --- |
| each `for` iteration | a child workflow |
| each `fork` branch | a child workflow |
| a `try` block (and its catch) | a child workflow |
| `run: workflow` | a child workflow of the given type, with its own Execution row |
| a switch case starting a named workflow | a child workflow of that name |
| `call`, `run` (script, shell, container) | activities |
| `set`, `switch`, `wait`, `listen`, `raise` | inside the workflow itself |

This is why Temporal's own history of a run is a poor picture of it, and why Duraflow collects
events from the worker instead; see [Run observability](/docs/architecture/observability).

A workflow with `document.metadata.canMaxHistoryLength` continues-as-new when its history grows
past that length. The backend always follows the latest run in the chain, so such a run is
reported correctly.

## Schedules

There is no schedule table. On every start, `zigflow run` deletes the Temporal schedule matching
the document's schedule id and recreates it if the document has a `schedule:` block. So saving
creates, updates or removes the schedule. The backend only handles what Zigflow can't see:

- deleting a workflow also deletes its schedule;
- changing the schedule id deletes the schedule under the old id.

When Temporal starts a scheduled run, there is no Execution row yet. The backend creates one when
the run's first event arrives, recognising it by Temporal's `TemporalScheduledById` search
attribute and matching its workflow type and task queue to a stored workflow. It gets the trigger
`scheduled`.
