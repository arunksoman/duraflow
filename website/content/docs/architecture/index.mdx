| Part | Built with | Responsible for |
| --- | --- | --- |
| [Frontend](/docs/architecture/frontend) | SvelteKit (Svelte 5), Svelte Flow, CodeMirror, Tailwind CSS with daisyUI | The builder and its DSL engine, the run views, every page. Talks to the backend only from its server side. |
| [Backend API](/docs/architecture/backend) | Go, Huma (OpenAPI 3.1) on Echo, GORM | Auth, projects, workflows and their versions, runs, workers; starting runs on Temporal; publishing schedules; collecting and streaming run events. |
| [Workers](/docs/architecture/execution) | The same Go binary, with Zigflow as a library | Executing every saved workflow, at the version each run started on, as real Temporal workers. |
| Temporal | Temporal server | Durability: history, timers, retries, child workflows, schedules. |

## The life of a workflow

1. **Design.** The frontend's DSL engine converts between the canvas and the Zigflow YAML,
   validating against the Zigflow JSON Schema. See [DSL to nodes](/docs/dsl/dsl-to-nodes).
2. **Save.** The backend validates the DSL with Zigflow and stores it as an immutable version, named
   by its content hash. It also publishes the workflow's schedule, if it has one. Nothing restarts.
   See [Execution](/docs/architecture/execution).
3. **Run.** Starting a run is a real `ExecuteWorkflow` call to Temporal, pinned to the current
   version. Temporal hands the work to any worker process, and provides durability, retries and
   timers.
4. **Observe.** The workflow reports every task's start, completion and failure, with inputs and
   outputs, as CloudEvents to the backend. The backend works out which run, loop iteration,
   branch or child workflow each event belongs to, stores it, and streams it to the browser, which
   replays it onto the canvas. See [Run observability](/docs/architecture/observability).

## Design principles

- **The DSL is the source of truth.** The canvas is derived from it; nothing about a workflow is
  stored anywhere else.
- **Nothing is simulated.** Runs execute on Temporal through Zigflow, and the UI shows what the
  workflow reported.
- **Every process can be copied.** API and worker processes keep no state of their own, so either
  scales by adding copies. See [Scaling](/docs/architecture/backend#scaling).
- **Runs are shown in the terms they were designed in,** not as Temporal event histories.
- **Everything the UI does is an API call,** documented by a generated OpenAPI spec. See
  [API](/docs/architecture/api).
