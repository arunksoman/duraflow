The backend is a Go service in `backend/`, built on [Huma v2](https://huma.rocks/) over
[Echo](https://echo.labstack.com/). Huma generates an OpenAPI 3.1 spec from the Go request and
response types, so the API documentation can't drift from the code. Workflows run through
[Zigflow](https://github.com/zigflow/zigflow), used as a Go library inside the same binary.

## Roles

One binary serves two roles, chosen with `DURAFLOW_ROLES`:

| Role | Does | Copies |
| --- | --- | --- |
| `api` | REST, live run streams (SSE), CloudEvents ingest, schedule publishing. One `api` copy at a time also runs the once-only jobs: completion watchers and event-log maintenance. | Any number |
| `worker` | The worker pool: one Temporal worker per task queue, running every saved workflow. See [Execution](/docs/architecture/execution). | Any number |

The default runs both in one process, which is what `docker compose up` does.

## Scaling

Neither role keeps state of its own, so both scale by adding copies behind whatever runs your
containers. Everything copies share lives in Postgres and Temporal:

- **Live run streams from any copy.** When a copy stores or resolves a run event, it sends a short
  reference through Postgres `LISTEN/NOTIFY`. Every copy with a browser watching that run reads
  the event and streams it, so no sticky sessions are needed. A copy that loses its `LISTEN`
  connection tells its streams to re-read the log when it reconnects.
- **Once-only jobs on one copy.** `api` copies compete for a Postgres advisory lock. The holder
  watches running executions for completion and maintains the event log. If it goes away, its
  session ends, another copy takes the lock within seconds and re-attaches a watcher to every
  running execution.
- **No duplicate work.** Saves of one workflow are serialised with an advisory lock. Migrations,
  the admin seed and the version backfill run under a startup lock, one copy at a time.
- **Workers follow saves at once.** A save notifies every worker copy to re-read its task queues.

Running separate roles or more than one copy requires Postgres; the backend refuses to start that
way on SQLite. Every copy must share `auth.jwtSecret` (tokens from one copy are checked by another,
and the CloudEvents token is derived from it) and the `ZIGGY_*` variables workflows read. A
worker-only copy also needs `telemetry.sinkURL`, pointing at an `api` copy's
`/api/internal/zigflow/events` on an internal address. The repository's
`docker-compose.scale.yml` runs Postgres, two `api` copies behind nginx and two `worker` copies.

## Structure

```
cmd/server/main.go        config, then app.New and app.Run until SIGINT/SIGTERM
internal/
  app/                    wires one process for its roles
  config/                 settings: defaults, optional YAML, DURAFLOW_* env vars
  db/                     opens SQLite or Postgres and migrates the schema
  models/                 User, Project, Workflow, DSLVersion, Execution, ExecutionEvent, Worker, ...
  auth/                   bcrypt password hashing, JWT issue and verify
  api/                    one file per resource; each registers its operations
  dslhash/                names a DSL version and carries it on every run in a Temporal header
  dslruntime/             Zigflow as a library: compile, cache, dispatch, worker pool
  coord/                  cross-copy messages, leader lock and locks (Postgres or in-memory)
  temporalexec/           Temporal client and event resolver
  events/                 fan-out of resolved run events to live watchers, across copies
data/                     SQLite database
```

## Data model

| Model | What it stores |
| --- | --- |
| `User` | Login accounts. |
| `Project` | A named group of workflows. |
| `Workflow` | Name, description and the **DSL text**; the `workflowType` and `taskQueue` read from its header; its current version (`currentHash`), or why its DSL doesn't build (`dslError`). |
| `DSLVersion` | One immutable DSL text, named by its SHA-256. Runs refer to it for their whole life. |
| `WorkflowRegistration` | Each Temporal workflow name a workflow's current version registers on its task queue. |
| `Execution` | One run: status, input, output, error, trigger (`manual`, `scheduled`, `backfill`), its Temporal ids and task queue, and for a child run its parent and the task that started it. |
| `ExecutionEvent` | One task event reported by a workflow, in receive order. See [Run observability](/docs/architecture/observability). |
| `WorkflowExecutionRef` | A cache of which run each Temporal workflow execution belongs to. |
| `Worker` | The Workers page's record of each worker process and the task queues it polls. |

Every model except `DSLVersion` and `WorkflowRegistration` has a UUID `id` and
`createdAt`/`updatedAt`. JSON fields are camelCase and mirror the frontend's types in
`frontend/src/lib/types/index.ts`.

## Persistence

SQLite is the default for a single process (a pure-Go driver, so no C toolchain is needed), in WAL
mode with a busy timeout, since workflows write events while the API reads. Postgres is supported
by configuration alone, and required for more than one process. The schema is migrated
automatically (GORM `AutoMigrate`) on every start; there are no migration files.

## Auth

`POST /api/auth/login` exchanges an email and password for a JWT. Every other API operation
requires `Authorization: Bearer <token>`; this is enforced by middleware that reads each
operation's declared security, so a new operation is protected unless it opts out. The one
exception is the internal endpoint workflows post run events to, which is authenticated with a
shared token instead. Keep it off your public load balancer; the bundled nginx config does.

When the users table is empty, an admin is created from the `seedAdmin.*` settings.

## Deleting things

Deletes cascade so nothing is left running or orphaned:

- **A run** is deleted with its child runs, its events, its cached references and, in the
  background, its Temporal history. A run still in progress is terminated first, if asked to
  (`force`), or the delete is refused.
- **A workflow** deletes its runs (terminating any in progress), its Temporal schedule and its
  registered names. Its DSL versions stay; they are immutable and may be shared.
- **A project** deletes each of its workflows that way, then itself.
