A Temporal workflow only runs if a **worker** is polling its task queue. Duraflow runs a pool of
identical worker processes that execute every saved workflow through Zigflow, so you never write
worker code and never start a worker per workflow. Saving is all it takes to make a workflow
runnable.

## The Workers page

**Workers** in the sidebar lists each worker process and the task queues it polls.

<Screenshot name="workers" alt="The Workers page listing each worker process, its task queue, status and last heartbeat" />

| Column         | Meaning                                                                                  |
| -------------- | ---------------------------------------------------------------------------------------- |
| Identity       | The worker process: `worker.identity`, by default `<hostname>:<pid>`.                    |
| Task queue     | A `taskQueue` the process polls. A process has one row per queue.                        |
| Status         | `online` while the process reports in; `offline` once it stops cleanly or misses three heartbeats. |
| Last heartbeat | When the process last reported in (every 10 seconds by default).                         |

A process that crashed or lost its host shows as `offline` within about half a minute. Rows of
processes gone for a day are removed.

## How the pool works

| Event                           | What happens                                                                 |
| ------------------------------- | ---------------------------------------------------------------------------- |
| A workflow is saved with steps  | Its DSL is stored as a new version. Every worker process starts polling the workflow's task queue within moments, if it wasn't already. Nothing restarts. |
| A run starts                    | Any worker polling the queue can pick it up. It loads the run's version, compiling it once and keeping it in memory. |
| A workflow is saved mid-run     | The run carries on with the version it started on; the next run uses the new one. |
| A worker process stops or dies  | Temporal gives its unfinished work to another worker once the task's timeout passes. |
| A workflow is deleted           | Its runs are terminated, and workers stop polling its queue once nothing else uses it. |

Each worker process runs one Temporal worker per task queue, not per workflow, so the number of
processes is up to you and doesn't grow with the number of workflows. Run more of them, on more
hosts, for more capacity or to survive losing a host; see
[Scaling](/docs/architecture/backend#scaling).

Workflow steps run inside the worker processes, so every worker host needs whatever those steps
need at run time, such as Python or Node.js for a BYOC script, or Docker for a container step.
Run task events reach the UI through the API; see
[Run observability](/docs/architecture/observability).
